# Factory Offering Strategy - Share Package

This folder is a self-contained handoff of the factory energy-offering
optimizer. It contains the scheduler implementation, install metadata, the
`uv` lockfile, a runnable set of example JSON inputs, a sample output, and
focused tests.

The model makes a day-ahead factory production schedule and energy bid curves,
then models intraday and real-time recourse, optional up-spinning-reserve
offers, reserve deployment, and profit-risk trade-offs using CVaR. It is a
command-line/Python package; **it does not expose an HTTP/UI service**.

## Package contents

- `factory_mt_offering_strategy.py`: offering model and Python API.
- `factory_mt_offering_cli.py`: offering command-line interface.
- `factory_mt_da_scheduler.py`, `factory_mt_id_scheduler.py`,
  `factory_mt_rt_scheduler.py`: shared underlying stages and data models.
- `factory_mt_production_rescheduler.py`: intraday production rescheduling.
- `factory_mt_offering_plotting.py`: optional plots.
- `pyproject.toml`, `uv.lock`: project metadata, entry points, and pinned
  dependency resolution.
- `examples/input/`: a 24-hour plant with both an MT and BESS, plus explicit
  DA/ID/SR, RT, and reserve-deployment JSON scenario files.
- `examples/output/`: output generated from those example inputs.
- `tests/`: focused tests for the offering integration.

## Requirements and install

Install Python 3.10 or later and [`uv`](https://docs.astral.sh/uv/). From this
folder (`Offering_Strategy_Handoff`) run:

```sh
uv sync --extra test
```

If your terminal is at the repository root, select the handoff project
explicitly:

```sh
uv sync --project Offering_Strategy_Handoff --extra test
```

`uv.lock` pins the resolved dependency versions. HiGHS is installed through
`highspy`; no separate solver installation is needed for the default
`appsi_highs` solver.

Run the focused tests:

```sh
uv run pytest
```

## Run the 24-hour example (MT + BESS)

The example plant has a 24-hour horizon, two machines, four production tasks,
one configured microturbine, and one configured battery. The first command
solves the day-ahead / intraday / real-time offering optimization and saves
tables and JSON output:

```sh
uv run factory-mt-offering \
  --instance examples/input/plant.json \
  --offering-scenario-file examples/input/offering_scenarios.json \
  --rt-file examples/input/rt_scenarios.json \
  --deploy-file examples/input/reserve_deployment.json \
  --out examples/output
```

If your terminal is at the repository root, use `--directory` so `uv` runs
inside the handoff project and resolves the relative example paths:

```sh
uv run --directory Offering_Strategy_Handoff factory-mt-offering \
  --instance examples/input/plant.json \
  --offering-scenario-file examples/input/offering_scenarios.json \
  --rt-file examples/input/rt_scenarios.json \
  --deploy-file examples/input/reserve_deployment.json \
  --out examples/output
```

To generate only the four selected figures in addition to the tabular outputs,
add `--plot`:

```sh
uv run factory-mt-offering \
  --instance examples/input/plant.json \
  --offering-scenario-file examples/input/offering_scenarios.json \
  --rt-file examples/input/rt_scenarios.json \
  --deploy-file examples/input/reserve_deployment.json \
  --plot --out examples/output
```

The four figures are `market_positions.png`, `market_prices.png`,
`production_schedule.png`, and `production_reschedule.png`. No profit
distribution, offering diagnostic, or stage-specific plots are generated by
the CLI's `--plot` option. MT and BESS settings are in
`examples/input/plant.json`; their hourly dispatch, battery SoC, and MT
commitment are available in the output CSV tables.

This example and its scenario arrays are synthetic and illustrative; they are
not live market data or market-ready bids. The CLI's `--help` lists additional
inputs, solver controls, risk settings, reserve controls, and analysis options.

## Inputs the UI/backend team should provide

The CLI accepts JSON files. In a service integration, the UI can collect the
same fields and the backend can validate/serialize them to these files or call
the Python API directly.

### Plant: `--instance plant.json`

| Field | Shape | Meaning |
|---|---|---|
| `machines`, `tasks` | lists | Machine and task identifiers |
| `power_mw` | `[machine][task]` | Task power draw in MW |
| `duration_h` | `[machine][task]` | Processing duration in hours |
| `yield_units` | `[task]` | Output quantity for each task |
| `base_load_mw` | `[hour]` | Non-task load in MW |
| `price_buy_eur_mwh`, `price_sell_eur_mwh` | `[hour]` | DA tariff input; sell must not exceed buy |
| `demand_units` | `[hour]` | Factory product delivery requirement |
| `horizon_h` | scalar | Number of hourly delivery periods |

Additional optional fields:

| Field | Unit / type | Meaning |
|---|---|---|
| `buffer_h` | hours | Required idle gap between consecutive tasks on the same machine. Default: `1.0`. Set to `0.0` if no changeover/cooling gap is needed. |
| `grid_limit_mw` | MW | Maximum power imported from the grid at any hour. Default: `400.0`. This is the import-side connection limit, not the factory's total load limit; local MT/BESS generation can serve load behind the connection. |
| `grid_sell_limit_mw` | MW | Maximum power exported to the grid at any hour. Default: `400.0`. This is separate from the import limit. |
| `max_batches_per_machine` | integer | Upper bound on the number of task batches scheduled on each machine over the horizon. Default: `10`. It limits the schedule; it does not create extra tasks or machines. |
| `inventory_init` | production units | Product stock available at the start of the horizon. Default: `50.0`. It must be between zero and `inventory_max`. |
| `inventory_max` | production units | Maximum on-site finished-product inventory at any hourly step. Default: `500.0`. The schedule must also finish with inventory at least as large as the starting stock. |
| `mt` | object or `null` | Optional microturbine configuration. If omitted, one MT is enabled with built-in defaults; `null` disables it. |
| `bess` | object or `null` | Optional battery configuration. If omitted or `null`, no BESS is enabled. |

Inventory is updated each hour from scheduled production minus that hour's
`demand_units`. The model keeps inventory nonnegative, below `inventory_max`,
and requires end-of-horizon stock to be at least `inventory_init`.

`mt` and `bess` take objects whose fields configure the respective single
aggregate resource. For example:

```json
{
  "mt": {
    "p_min_mw": 10.0,
    "p_max_mw": 25.0,
    "ramp_up_mw_h": 20.0,
    "ramp_down_mw_h": 20.0,
    "initial_on": false
  },
  "bess": {
    "p_max_mw": 40.0,
    "e_max_mwh": 200.0,
    "soc_init_mwh": 20.0,
    "eta_ch": 0.8,
    "eta_dis": 0.95,
    "degradation_eur_mwh": 35.0,
    "degradation_basis": "throughput"
  }
}
```

MT fields cover its minimum/maximum output, ramp limits, startup/shutdown
costs, minimum on/off times, fuel-cost blocks, and initial on/off state and
power. Defaults are `p_min_mw: 10`, `p_max_mw: 25`, ramp limits
`20 MW/h`, startup/shutdown costs `87.40/8.74 EUR`, minimum up/down times
`4/2 h`, and an initially-off state. Fuel-cost block widths must sum to
`p_max_mw - p_min_mw`, and their marginal costs must be non-decreasing.

BESS fields cover charge/discharge power (`p_max_mw`), energy capacity
(`e_max_mwh`), SoC limits as fractions of capacity (`soc_min_frac`,
`soc_max_frac`), initial SoC (`soc_init_mwh`), efficiencies (`eta_ch`,
`eta_dis`), degradation cost/basis, and whether simultaneous charging and
discharging is forbidden (`enforce_exclusive`). Defaults are 40 MW / 200 MWh,
10% / 90% SoC limits, 20 MWh initial SoC, 0.80 / 0.95 efficiency, and
35 EUR/MWh throughput degradation. `degradation_basis` must be either
`"throughput"` or `"discharge"`.

In this model, the task definitions are a machine-by-task matrix rather than
an arbitrary list of independent work orders. The MT and BESS objects
configure one aggregate resource each; they do not define multiple individual
units.

### Price uncertainty: `--offering-scenario-file offering_scenarios.json`

Let `S` be the number of price scenarios and `T` be the plant horizon.
`prob` is `[S]`; the price/deviation arrays are `[S,T]`.

| Field | Unit | Meaning |
|---|---|---|
| `da_buy`, `da_sell` | EUR/MWh | DA buy/sell scenarios |
| `id_buy`, `id_sell` | EUR/MWh | ID buy/sell scenarios |
| `sr_up` | EUR/MW/h | Up-reserve capacity price |
| `load_dev_mw` | MW | Additive deviation from the plant base-load forecast |

Scenario probabilities must sum to one. Sell prices must not exceed buy prices.

### Real-time and reserve: `--rt-file` and `--deploy-file`

These files describe what may happen **after** a day-ahead/intraday price path
has been selected: actual factory load may differ from forecast, balancing
prices may differ, and the system operator may activate some of the offered
up-reserve.

#### Dimensions and indexing

- `T` = number of hourly periods in the plant file (`horizon_h`). For a
  24-hour plant, valid time indexes are `t = 0..23`; index `0` is the first
  hour, not hour 1.
- `S` = number of price paths in `offering_scenarios.json`. The same `s`
  identifies the DA, ID, and reserve price path at that scenario index.
- `W` = number of **conditional real-time branches for each** price path. It
  is not the total number of joint scenarios. The optimizer combines every
  price path with its RT branches, giving `S * W` joint paths.

Arrays use row-major order `[s][w][t]`: first choose price scenario `s`, then
its RT branch `w`, then the hour `t`. In the supplied 2-scenario, 2-branch,
2-hour example:

- `prob[0][1]` is the probability of RT branch 1, conditional on price path 0.
- `load_rel_dev[0][1][0]` is the load deviation in hour 0 on that path.
- `rho[0][1][0]` is the reserve call fraction in that same price/RT/hour cell.

The joint probability of a cell is
`offering_scenarios.prob[s] * rt_scenarios.prob[s][w]`. RT probabilities are
conditional on their corresponding price scenario; each row in `prob` must
sum to 1.

#### `rt_scenarios.json` (`--rt-file`)

All four keys are required:

| Key | Shape | Unit | Meaning |
|---|---|---|---|
| `prob` | `[S,W]` | probability | Conditional probability for each RT branch under each price scenario. Values must be nonnegative; each scenario row sums to 1. |
| `load_rel_dev` | `[S,W,T]` | fraction | Relative deviation from the factory's **Stage-2 planned total load**. Actual load is `(1 + load_rel_dev[s][w][t]) * (base_load[t] + scenario_load_dev[s][t] + scheduled_batch_load[t])`. Thus `0.02` means 2% more load and `-0.02` means 2% less load. It is not an MW value. Every value must be greater than `-1`, so actual load cannot become negative. |
| `r_plus` | `[S,W,T]` | multiplier | Imbalance deficit/buy price multiplier. The deficit settlement price is `r_plus * price_buy_eur_mwh[t]`. Must be at least 1, so a deficit is not priced below the DA buy tariff. |
| `r_minus` | `[S,W,T]` | multiplier | Imbalance surplus/sell price multiplier. The surplus settlement price is `r_minus * price_sell_eur_mwh[t]`. Must be between 0 and 1, so surplus is not paid above the DA sell tariff. |

The same `r_plus` / `r_minus` value is applied to the plant's per-hour DA
tariff arrays in `plant.json`. In the strategic offering run these ratios are
provided for each `(s,w,t)` cell even though the underlying plant tariff is
the reference tariff. They are not prices in EUR/MWh themselves.

For example, if an hour's plant buy tariff is EUR 100/MWh and
`r_plus[s][w][t]` is `1.2`, a deficit in that cell settles at EUR 120/MWh. If
the sell tariff is EUR 55/MWh and `r_minus[s][w][t]` is `0.8`, surplus settles
at EUR 44/MWh.

#### `reserve_deployment.json` (`--deploy-file`)

This file contains one required key:

| Key | Shape | Unit | Meaning |
|---|---|---|---|
| `rho` | `[S,W,T]` | fraction | Fraction of the cleared/offered up-reserve activated in each price-scenario, RT-branch, hour cell. Values range from `0` (no activation) to `1` (full activation). |

`rho` is a fraction, not MW. The model applies it to the reserve quantity
decided by the optimizer: the activated quantity is conceptually
`rho[s][w][t] * reserve_offer_mw[s][t]`. The reserve offer itself is split
between eligible assets (MT, battery charge/discharge, and/or demand response)
according to the configured reserve assets. Activation then affects physical
grid exchange and limits, battery state of charge, MT fuel, demand-response
compensation, and activation-energy revenue. It is an assumed scenario input;
it is not a signal received from a live system operator.

#### Shape and data checks

For every file, array lengths must agree with the plant and offering scenario
file:

- `rt_scenarios.prob.shape` must be `[S,W]`, with `W >= 1`.
- `load_rel_dev`, `r_plus`, and `r_minus` must each have exactly `S` rows,
  `W` branches per row, and `T` values per branch.
- `reserve_deployment.rho` must have exactly the same `[S,W,T]` shape.
- `S` must equal the number of rows in the offering price arrays; `T` must
  equal `horizon_h`.
- Probabilities and `rho` must be in `[0,1]`; conditional RT probabilities
  must sum to 1 for each `s`.
- Use JSON numbers, not numeric strings or `null`, for array values.

In the example files, `S=2`, `W=2`, and `T=2`. Under price path 0, RT branches
0 and 1 each have probability 0.5. In price path 0 / RT branch 1, the relative
load deviation is `[+2%, -2%]` over the two hours, while `rho` is `[0.1, 0.0]`:
10% of the optimized reserve is called in the first hour and none in the
second. That cell's joint probability is `0.5 * 0.5 = 0.25`.

The bundled files under `examples/input/` are only a shape/value example.
Real use should replace them with calibrated forecasts or assumptions for the
same horizon and scenario tree. When replaying output, use the matching
`scenario_set.json`, `rt_set.json`, and `deployment_set.json` saved by that
run.

## Outputs the UI can consume

Every run writes an output folder. Most useful files for integration are:

- `bid_package.json`: market-facing per-hour energy bid and reserve offer price
  / quantity curves, plus the strategy parameters.
- `jobs.csv`: selected shared production plan with machine, task, start/end,
  power, and output.
- `da_position.csv`: hourly DA position, MT/BESS schedule, reserve quantities,
  and expected operating values.
- `hourly_offering.csv`: detailed per-hour offering and expected dispatch.
- `offer_curves.csv`: normalized/long-form offer curve rows.
- `summary.json`: solver status, expected and risk-adjusted objective, CVaR,
  KPI breakdown, solve statistics, and independent verification.
- `scenarios.csv`, `joint_scenarios.csv`: scenario-level details.
- `scenario_set.json`, `rt_set.json`, `deployment_set.json`: saved scenario
  inputs used by the run.
- `intraday_rescheduled_jobs.csv` and `intraday_reschedule_summary.csv`:
  scenario-specific production-only intraday schedules and matched comparisons
  with the fixed day-ahead task schedule.
- With `--plot`, only `market_positions.png`, `market_prices.png`,
  `production_schedule.png`, and `production_reschedule.png` are generated.
  With `--compare`, strategy and market-stage comparison CSVs are generated.

`expected_net_cost_eur` is not total factory profit: product-sales revenue is
not included. Intraday production-rescheduling savings are reported separately
and are not included in the offering objective.

## Backend/UI integration notes

1. Keep each plant configuration, operating date, and day-ahead result
   associated with the same run.
2. Return `bid_package.json`, `jobs.csv`, and selected KPI fields to the UI
   after a successful solve; surface validation and solver failures instead of
   returning an empty or stale schedule.
3. For repeatable scenario studies, send explicit scenario files. If those
   files are omitted, the CLI generates synthetic scenarios.
4. The current CLI runs the complete configured study. It is not an
   asynchronous job service, live data connector, or rolling-horizon endpoint.
   Those pieces must be supplied by the integrating backend.
5. These results are optimization outputs, not a guarantee of market
   acceptance, dispatch, revenue, or compliance with a particular exchange's
   bid increments and gate-closure rules.
